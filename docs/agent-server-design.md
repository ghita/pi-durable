# Agent server v1 design (draft)

**Status:** Proposed for review. This is a design sketch, not an implementation contract yet.

## Goal

Run one server instance with a configured catalog of independently developed agent implementations. A client connects to that server, discovers its catalog, creates an agent-bound thread, and starts or continues work. Each server is independently deployed and addressed by URL. There is no hub or global catalog.

The server is an adapter and host for agent implementations; it does not require the implementations to use LangGraph. `@langchain/protocol` is the source for the common command/event semantics. Each implementation gets a generic protocol-shaped host adapter; it does not inherit the API of `ResearchRunAgent` or another specific agent. This project owns catalog discovery, module loading, server lifecycle, thread identity/binding, authentication, and any client SDK.

## Confirmed decisions

- A server loads its agent catalog from local configuration, in the style of `langgraph.json`.
- Agents are selected from the catalog exposed by the connected server. Remote agent services and a cross-server hub are out of scope for v1.
- A thread is explicitly created for one registered agent and is permanently bound to it.
- Thread IDs may be supplied by the client or generated by the server.
- Duplicate IDs raise by default. `do_nothing` returns an existing thread only when it is bound to the requested agent; otherwise return `409 Conflict`.
- A research case gets a new thread. Clarification and continuation stay in that thread.
- Different agents may define different thread interaction policies, surfaced through their descriptors.
- Use `@langchain/protocol` at the wire boundary, not the LangGraph runtime/server. The protocol is draft, so isolate it behind an adapter.

## Proposed module layout

Add a server library (provisionally `packages/agent-server`) with four responsibilities:

1. **Catalog loader** — reads the server manifest and imports configured agent factories at startup.
2. **Agent host contract** — the in-process interface each configured agent adapter implements.
3. **Protocol/HTTP adapter** — validates requests, routes them to the bound agent, and converts agent updates into protocol events.
4. **Typed client** — discovers agents, creates/attaches to threads, issues commands, and consumes event streams.

A small executable in this repository composes the library with the configured catalog. Each agent-specific integration adapts its native runtime to the generic host contract. `ResearchRunAgent` is one candidate adapter and conformance test, not the template that defines the contract.

## Proposed catalog manifest

Use an explicit ID-to-module-export map. This is a proposal; exact filename and factory signature remain open.

```json
{
  "agents": {
    "deep-research": "./src/server/deep-research-adapter.ts:createAgent"
  },
  "env": ".env"
}
```

On startup, the server imports each entry, validates that the exported descriptor ID matches its manifest key, and refuses to start if a module cannot load or IDs are duplicated. The code named by the manifest is trusted server code with the server process's privileges; this is not a sandbox or remote-plugin mechanism. Catalog changes require a server restart in v1.

A discoverable descriptor should include at least:

```ts
type AgentDescriptor = {
  id: string;
  name: string;
  description: string;
  inputSchema?: JsonSchema;
  threadPolicy: "single-case" | "multi-turn";
  capabilities: Array<"interrupts" | "streaming" | "cancel">;
};
```

This lets clients render an appropriate interaction without making the server understand agent-specific workflow state. More policy values can be added additively.

## Proposed generic agent host contract

Derive this contract from the protocol's command/event model and shared hosting needs—not from the methods of any one agent. Each manifest entry creates one runtime per server process. The host handles HTTP, auth, catalog lookup, thread ownership, and stream subscriptions. It validates protocol commands, enforces that the command's `assistant_id` matches the immutable thread binding, then dispatches the supported run/input/state command to the selected runtime. The runtime returns protocol-compatible command responses and publishes protocol-compatible events for that thread.

Conceptually, the runtime contract is:

```ts
interface HostedAgent {
  descriptor: AgentDescriptor;
  initialize(): Promise<void>;
  createThread(thread: { threadId: string; agentId: string; metadata?: Record<string, unknown> }): Promise<void>;
  handleCommand(threadId: string, command: AgentCommand): Promise<AgentCommandResult>;
  subscribe(threadId: string, filter: EventStreamRequest): AsyncIterable<AgentEvent>;
  close(): Promise<void>;
}
```

`AgentCommand`, `AgentCommandResult`, `EventStreamRequest`, and `AgentEvent` are version-neutral host types with a deliberately direct mapping to `@langchain/protocol` `Command`/response/event types. The protocol adapter owns wire serialization/versioning. Agent authors implement generic run/input/state behavior or adapt their native framework to it; they do not implement bespoke HTTP routes. Thread-specific workflow policy and persisted state remain agent-owned.

Command admission must be idempotent for a stable request/command ID, or return an explicit failure that tells clients whether retry is safe. The host must preserve the protocol's response/event correlation while keeping any internal run IDs private unless the protocol exposes them.

## Request/response mapping flow

Yes: this is explicit server code, with two distinct pieces of responsibility—not automatic reflection over arbitrary agents.

1. **Catalog loader:** reads the manifest, imports each module, invokes its factory, validates the descriptor, and stores `agentId -> HostedAgent` in the server registry.
2. **Shared protocol bridge:** for a request, resolves the thread, checks its immutable `agentId`, validates the command, and dispatches it to that registered `HostedAgent`. It sends the command response back as the protocol response and forwards the agent's protocol events to the caller's SSE stream.
3. **Per-agent adapter:** each agent implementation (or its adapter) maps the generic protocol command into its native API and maps its results/progress/errors back into protocol responses/events. The bridge is shared; these semantic mappings are agent-specific.

```text
manifest → catalog loader → registry[agentId] = HostedAgent
client command → HTTP/protocol bridge → registry[thread.agentId].handleCommand(...)
client SSE     ← HTTP/protocol bridge ← registry[thread.agentId].subscribe(...)
```

For example, the server does not know what “answer clarification” means. It receives a generic protocol input response, dispatches it to the agent bound to that thread, and the ResearchRun adapter translates it to its own clarification mechanism. Another agent can interpret the same protocol-level continuation according to its declared thread policy without changing the loader, routes, or client.

## Proposed HTTP surface

Use a versioned REST surface for catalog and durable resources, and protocol commands/events for run interaction:

| Endpoint | Purpose |
|---|---|
| `GET /v1/agents` | Discover this server's configured catalog and descriptors. |
| `GET /v1/agents/:agentId` | Read one descriptor. |
| `POST /v1/threads` | Create a thread with `{agentId, threadId?, ifExists?, metadata?}`. |
| `GET /v1/threads` | List threads visible to the caller, with pagination. |
| `GET /v1/threads/:threadId` | Read thread identity, bound agent, status, and current-run summary. |
| `POST /v1/threads/:threadId/commands` | Submit an `@langchain/protocol` command, initially `run.start` and `input.respond`. |
| `POST /v1/threads/:threadId/stream` | Subscribe to protocol events over SSE; use event IDs/cursors for reconnect where supported. |

Every `run.start` must name the same `assistant_id`/agent ID bound to the thread; a mismatch is `409 Conflict`. Protocol framing, unknown-field handling, error envelopes, and replay guarantees need contract tests before v1 is considered stable.

The server should expose a small set of generic lifecycle events. Agent-specific phases and structured progress use protocol custom events rather than new server routes. A clarification is an input request; its answer continues the bound thread. A final report is an agent result/message, not a server-specific route.

## `ResearchRunAgent` as a conformance adapter

The server contract must not be shaped around `ResearchRunAgent`. It should be possible to replace it with an independently authored agent without changing server routes, client code, or the protocol adapter.

Use the research workflow only to prove the generic contract: implement an adapter that maps protocol commands and events to its existing service API. That adapter may privately translate `run.start` to `start()`, a clarification response to `answerClarification()`, and its snapshots/watch stream to protocol events. Those method names, its internal `RunId`, its single-request policy, and its per-run SQLite layout must not appear in the generic host interface or server wire contract.

The research agent declares its single-case thread policy: a research thread accepts the initial case and its clarification/continuation; after completion or failure, a different case requires a new thread. Its adapter is responsible for preserving the mapping to its internal durable identity and recovering it after restart. The server stores only host-owned thread identity, immutable agent binding, metadata, access/idempotency records, and opaque adapter references if needed. It must not copy the agent's checkpoints into a second store.

## Proposed execution and recovery defaults

- Different threads may run concurrently, bounded by server configuration.
- At most one active run per thread. A conflicting new run is rejected as busy in v1; no queue/steer/rollback policy until demanded.
- Closing an HTTP/SSE connection does not cancel durable work. Clients reconnect and read a fresh thread/run snapshot before resuming the stream.
- On process startup, the host initializes configured agents and asks each adapter to recover its active threads. If an agent fails to initialize, fail startup with the agent ID and cause rather than silently serving an incomplete catalog.
- One server process owns a given local data directory in v1. Horizontal multi-process execution/shared storage is out of scope.

## Proposed security defaults

The existing research service is single-tenant. For an initial remotely reachable server, use one configured bearer token for all `/v1` routes; all authenticated clients can discover/use all agents and threads. Bind to loopback by default and require HTTPS or a trusted TLS-terminating reverse proxy for remote access. The bearer token grants execution with the privileges of the server process; it is not per-agent authorization or a sandbox. Multi-user ownership, per-agent ACLs, and OAuth are out of scope for the first cut.

## Protocol dependency boundary

`@langchain/protocol` currently publishes TypeScript bindings for a draft protocol, not a server implementation. Keep imports in one protocol adapter and translate to stable project-owned domain types internally. Pin the version and add wire fixtures/contract tests. Do not depend on `@langchain/langgraph`, `@langchain/langgraph-api`, or `@langchain/langgraph-cli` in the server core.

The LangGraph JS SDK contains a reusable protocol stream adapter, but adding it would be optional client interoperability—not a server dependency. Evaluate it separately after the server routes and compatibility tests exist.

## Out of scope for v1

- A central hub/global catalog or remote module loading.
- Dynamic catalog reload without restart.
- Cross-agent threads or moving a thread to another agent.
- Arbitrary state-schema inspection/editing across unlike agent implementations.
- A generic UI; the client SDK and agent descriptors are the reusable surface.
- Multi-tenant authorization and horizontal scaling.

## Review points before implementation

1. Review the generic protocol-shaped host contract and the descriptor/capability vocabulary.
2. Confirm one active run per thread with reject-on-busy for v1.
3. Agree whether a basic bearer token is sufficient for the first remotely reachable deployment.
4. Finalize idempotency behavior for ambiguous retries, especially when an adapter starts durable work but the server loses the response.
